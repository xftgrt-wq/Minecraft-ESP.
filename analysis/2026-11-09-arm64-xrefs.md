# ARM64 binary analysis — 2026-11-09

Target: the supplied Minecraft Bedrock Android `libminecraftpe.so` (ELF64 AArch64).

## Confirmed tooling and method

- LLVM objdump 17 in this environment supports AArch64 disassembly.
- The `.text` section was disassembled around references to selected strings in `.rodata`.
- A scan of AArch64 `ADRP` + `ADD` instruction pairs located direct code references to several strings.

## Findings

| String | Code reference(s) | What the inspected code establishes |
|---|---:|---|
| `MinecraftCamera::CameraComponent` | 27 references; examples: `0x0860EE40`, `0x0873D100` | The type name is used in several component/type-check or diagnostic paths. These are not verified camera-matrix accessors or render hooks. |
| `ScriptModuleMinecraft::ScriptItemActorComponent` | `0x0ECB8C64` | The code stores the type-name address and length in a metadata/error-description structure. This is not item enumeration. |
| `GlobalActorComponent` | `0x0BDD264C`, `0x0C7B0D5C` | References occur in component-related code, but no entity iteration contract or stable component layout is established. |
| `ActorEventCoordinator::sendActorDroppedItem` | `0x10A9D3FC` | The inspected code passes the name as diagnostic metadata to another routine. This does not establish a safe hook at that address. |
| `AddItemActorPacket` | `0x0D3E4BD8` | The code returns a pointer/length pair for the packet name with an error/status value. It is not the packet handler. |
| `TakeItemActorPacketPayload` | `0x0E03128C` | The string is used in a validation/error path. It is not a render callback. |

The strings `LevelRendererPlayer::preRenderUpdate(...)`, `LevelRendererPlayer::tickClouds(...)`, and `DataDrivenRenderer::render(...)` are present, but no direct `ADRP` + `ADD` code reference to those exact string addresses was found by the current scan. Their presence alone does not identify callable function addresses.

## Conclusion

No verified function address, calling convention, entity-list layout, camera matrix layout, or HUD/render submission point has been established. The offsets above are **analysis locations only**, not hook addresses. Patching them or using them as function pointers would be unsafe.

4. Validate each candidate against this exact binary before implementing any hook.

The native library in this repository remains a build prototype, not a functional ESP.
