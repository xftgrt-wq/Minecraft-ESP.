# 2026-11-09 — трассировка конструирования LevelRendererCamera

## Новые результаты по бинарнику 1.26.33 ARM64

### 1. Найден прямой вызов конструктора
Поиск инструкций AArch64 `BL` по всему сегменту `.text` дал один прямой вызов конструктора по адресу `0xbd62060`:
- callsite: `0xbd7ad48`;
- перед вызовом caller помещает `x19` в `x0`;
- конструктор устанавливает vptr `0x141d14f8` в начало объекта.

Это подтверждает реальный путь создания объекта, использующего таблицу `LevelRendererCamera`, а не только существование RTTI/vtable-данных.

### 2. Контекст вызывающей функции
В вызывающей функции перед конструктором выполняются операции очистки/освобождения нескольких временных объектов и ветвление по состояниям. Само имя функции caller из stripped ELF надёжно не восстановлено. Поэтому нельзя приписывать ей конкретное имя метода игрового движка.

### 3. Дополнительные пути
Функция `0xbd79250` вызывается напрямую из двух мест:
- `0xbd7b5e4`;
- `0xbdc5348`.

В одном из caller-контекстов после вызова инициализируется крупный объект с полями вплоть до смещения `0xdb8`, включая несколько указателей на структуры рендеринга. Это поддерживает связь исследуемого кластера с инициализацией render/camera-подобных объектов, но само по себе не устанавливает назначение каждого поля.

### 4. Что ещё не доказано
- Не найдено однозначное место вызова виртуального слота `+0xc0` именно на объекте `LevelRendererCamera`.
- Не установлено, какой uniform-буфер содержит `CurrentViewProjectionMatrixUniform`.
- Не получены layout/offset ECS-компонентов сущностей.
- Ни один из найденных адресов пока не является готовым безопасным хуком.

## Следующий шаг
Сопоставить соседние vtable и RTTI complete-object-locator, затем разобрать функцию `0xbd79250` и связанные поля объекта, чтобы определить границы camera/render-subobject и возможный путь к uniform descriptor.
