# 2026-11-09 — уточнение назначения матричных блоков камеры

## Важное уточнение к предыдущему отчёту
Повторно разобрана функция `0xbd9c4d0` целиком и место её вызова из `0xbd6f97c`.

Функция `0xbd9c4d0` записывает выходную структуру размером не менее `0x58` байт. В ней есть:
- float-поля и пары/тройки float;
- нулевые служебные поля;
- флаг по смещению `+0x54`;
- вычисления с тригонометрическими константами, нормализацией вектора и проверкой дополнительных параметров.

В вызывающем методе из этой структуры копируются 4 последовательных 16-байтовых блока с offsets `+0x14`, `+0x24`, `+0x34`, `+0x44` в объект камеры по offsets `+0xd30`, `+0xd40`, `+0xd50`, `+0xd60`.

## Более точная интерпретация
Четыре блока подряд занимают 64 байта и по размеру совместимы с матрицей 4×4. Но они являются частью более крупной структуры, которую helper формирует из угловых/векторных параметров. Поэтому их разумно считать кандидатом на матрицу ориентации/преобразования камеры, а не доказанной матрицей `CurrentViewProjection`.

Предыдущая формулировка «найдена матрица 4×4» была слишком сильной. Подтверждены 64 байта матрично-подобных данных; математическая роль не установлена.

## Отдельная проверка регистрации CurrentViewProjection
Инициализатор, содержащий строку `CurrentViewProjectionMatrixUniform`, по адресу `0x1290cf28` передаёт адрес строки в общий helper `0xe570a9c`, затем descriptor-подобный объект передаётся в `0x1261014c` и сохраняется в static storage около `0x149100a0`.

Это подтверждает регистрацию именованного uniform descriptor, но не раскрывает место, где GPU-буфер получает фактическое значение матрицы. Регистрация имени и runtime upload — разные операции.

## Следующие направления

2. Проследить поля объекта камеры `+0xd30..+0xd60` до GPU update и проверить, совпадают ли они с descriptor.
3. Параллельно перейти к ECS: от подтверждённых `StateVectorComponent`, `HitboxComponent`, `AABBShapeComponent` найти реальные storage/registry access paths, не подменяя type metadata runtime layout.
